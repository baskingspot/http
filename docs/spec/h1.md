# HTTP/1.1 head parsing: references and choices

The parser in `src/h1/root.zig` is written from the RFCs, not ported from C.
`picohttpparser` supplied the incremental-read contract (`SearchState`) and its
test corpus informed the table below; `hparse` 0.2.0 is kept as a benchmark
reference, not as a base.

## Normative references

- [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112): HTTP/1.1 message syntax
  and routing. §2.1 message format, §2.2 parsing and line terminators, §2.3
  HTTP-version, §3 request line, §3.1 method, §3.2 request-target, §4 status
  line, §5 field syntax, §5.1 field line parsing, §5.2 obs-fold.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110): HTTP semantics. §2.5
  protocol version semantics, §6.2 control data and the higher-minor rule,
  §5.1 fields, §5.5 field values, §5.6.2 token and
  tchar, §5.6.3 OWS, §15 status codes.
- [RFC 5234](https://www.rfc-editor.org/rfc/rfc5234): ABNF core rules.
- [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986): URI syntax, referenced by
  the request-target forms.

## Choices where the RFC permits more than one behavior

| Subject | RFC | Choice |
| --- | --- | --- |
| Bare LF as a line terminator | 9112 §2.2 (MAY recognize) | Accept. A line end is LF or CRLF in the start line and field lines. A bare CR is `Invalid`. |
| Chunk framing line ends | 9112 §7.1 | CRLF only. These bytes decide where the next message starts. |
| Lenient start-line whitespace | 9112 §3, §4 (MAY parse on whitespace) | Reject; exactly one SP. |
| obs-fold | 9112 §5.2 (reject or unfold) | Reject. |
| Whitespace before the first field | 9112 §2.2 (reject or consume) | Reject. |
| Leading empty lines before a request-line | 9112 §2.2 (SHOULD ignore) | Skip any number. |
| Minor version above 1 | 9110 §6.2 (process as highest supported) | Map to 1.1; keep the wire pair in `wire_version`. |
| Status codes outside 100..599 | 9110 §15 (invalid) | Return the three digits as an open `Status`; the caller applies the class rule. |
| Request-target form | 9112 §3.2 | No whitespace and printable ASCII; `targetForm` classifies origin, absolute, authority, and asterisk. Routing stays with the caller. |
| Missing or duplicate Host | 9112 §3.2 (server MUST 400) | `host` returns the single value or `error.DuplicateHost`; the caller applies the HTTP/1.1 400. |
| Interim responses | 9110 §15.2 | `parseResponse` returns a 1xx head like any other; the caller parses again for the final response. |
| Header storage exhaustion | — | `error.TooManyHeaders`, distinct from invalid syntax. |

## Lifetimes

`parseRequest` and `parseResponse` return a head that borrows the input buffer
and the caller's `Header` storage. The head is valid only while both are
unchanged. A buffered reader may move its bytes when it refills or rebases;
copy the target, reason, and any field values needed later before the next read
or rebase. The parsed `method`, `version`, and `wire_version` are plain values.

## Incremental reads

`SearchState` carries the number of bytes already searched for the head
terminator, which is two line ends in a row: `LF LF`, `LF CRLF`, `CRLF LF`, or
`CRLF CRLF`. Keep one per connection buffer. On a later call the completeness
check starts at `searched - 4`, so only new bytes are scanned; parsing still
starts at byte 0. A client trickling one octet at a time therefore cannot force
a full rescan on every read. The parser clears the state after a complete parse.

## Message body framing

`h1.framing` applies RFC 9112 §6.3 in order. `request` returns a
`RequestBody`: `none`, `length`, or `chunked`. `response` returns a
`ResponseBody`, which adds `close` and `tunnel`. It reads the head only; it
does not read the body.

| Subject | RFC | Choice |
| --- | --- | --- |
| HEAD, 1xx, 204, 304 | 9112 §6.3 rule 1 | `none`, whatever the fields say. |
| 2xx response to CONNECT | 9112 §6.3 rule 2 | `tunnel`; ignore Content-Length and Transfer-Encoding. |
| Transfer-Encoding and Content-Length together | 9112 §6.3 rule 3 (TE overrides, ought to be an error) | Reject as `error.ConflictingFraming`. |
| Transfer-Encoding on HTTP/1.0 | 9112 §6.1 (faulty framing) | Reject as `error.FaultyFraming`. |
| Transfer-Encoding on a request, final coding not chunked | 9112 §6.3 rule 4 (server MUST 400) | Reject as `error.InvalidTransferEncoding`. |
| Transfer-Encoding on a response, final coding not chunked | 9112 §6.3 rule 4 | `close`. |
| Content-Length, no Transfer-Encoding | 9112 §6.3 rule 6 | `length`; malformed, conflicting, or overflowing values are `error.InvalidContentLength`. |
| Request with no framing fields | 9112 §6.3 rule 7 | `none`. |
| Response with no framing fields | 9112 §6.3 rule 8 | `close`. |

`chunked` takes no parameters and must appear at most once. The framing result
is the input to the chunked decoder.

## Chunked bodies

`h1.chunked.Decoder` decodes RFC 9112 §7.1. `next` returns a `Step`: a borrowed
data slice, the trailer `Headers`, or `need_more`. `consumed` is the prefix to
drop on every step, including `need_more`, so the caller can append bytes and
retry without copying the whole body. A chunk data slice may end before the
chunk does; the decoder remembers the remaining count.

Chunk extensions are parsed and ignored. A chunk size that does not fit `u64`
is `error.Overflow`; a malformed size, CRLF, extension, or trailer is
`error.Invalid`. Trailers are returned separately; the caller decides which
fields can be merged (RFC 9110 §6.5.1).

## Connection persistence

`h1.persistent(version, headers)` applies RFC 9112 §9.3. HTTP/1.1 persists by
default; HTTP/1.0 persists only with the `keep-alive` connection option; a
`close` option wins on either version.

## Writer

`h1.Writer` carries a caller-owned `*std.Io.Writer`; it never creates, flushes,
or closes one. The grammar is the parser's: CRLF only, `tchar` field
names, field-value bytes, and printable ASCII targets. `requestLine` and
`statusLine` write the start line, `field` and `endFields` the field section,
and `contentLength` or `chunked`/`chunk`/`lastChunk` the body framing. A known
body length is caller-supplied; a streaming body uses chunked. The checked methods reject invalid names, values, targets, methods, and
reasons before writing; the `assume*` variants skip that validation for trusted
data. An empty chunk is rejected by both.

## Server connection

`h1.ServerConn` is a state machine over one connection. The caller supplies
the request buffer, the field storage, the response head buffer, and the time.
The machine allocates no memory and touches no socket. The response head
buffer must hold the status line, the machine's fields, and the caller's extra
fields; `init` requires at least 64 bytes.

Call `start` after accept, before the first read. It starts the idle timer.
Without it a silent connection has no deadline. The first input byte starts
the head and total request timers.

The loop:

1. Call `recvBuffer`. Read into the returned slice.
2. Call `received`. Handle `need_more`, `request`, `reject`, or `closed`.
3. After `request`, call `respond`.
4. Call `sendSlices`. Write the head and the body.
5. Call `sent`. `more` repeats step 4. `read` means read the request body;
   the 100 Continue response is complete. `keep_alive` returns to step 1.
   `close` ends the connection. `close_after_drain` means drain the raw socket
   into scratch storage until `deadline`, then close.

After `keep_alive`, call `advance` before the next read. It parses a pipelined
request already in the buffer. `sent` starts the idle timer when it returns
`keep_alive`, so an idle connection still has a deadline. Call `eof` when the
peer closes. Call `tick` when the poll deadline expires. `tick` covers every
phase: a head, body, or application timeout queues a 408; a response timeout
closes the connection; an expired drain closes.

After `sent` returns `close_after_drain`, `recvBuffer` is empty. Read into a
scratch buffer and discard the bytes; `received` accepts only a head or body
phase, not a drain. Close on EOF, or when `tick` returns `close` at the drain
deadline. A reject that leaves a request body unread uses this result, so a
reset does not discard the error response. `drain_timeout` bounds the drain; a
zero duration skips the drain and returns `close`.

By default the machine buffers the whole request body in the request buffer.
A body over `body_bytes` is 413. A chunked request body is 501 for now. When the
head is complete but the body is not, `received` returns `request_head` with the
head and the content length. The caller can respond immediately, or call
`acceptBody(storage)` to choose the body destination. Bytes already in the
request buffer are copied there once; subsequent reads go straight there.
`bufferBody` selects the default request-buffer path. A body over the chosen
storage is 413.

After that early response the raw input is drained before closing rather than
misread as the next request. The total request deadline covers head delivery;
the body deadline starts when a sink is chosen.

A caller serving a TLS layer or another transport with a minimum read size can
set `Limits.min_read_bytes`. When an incomplete head or default-buffered body
has less free space than that, the machine returns 431 for a head and 413 for a
body instead of stalling. Zero preserves the previous behavior.

For protocol upgrades, `switchProtocols` queues a 101 response. The caller
supplies `Connection: Upgrade` and owns Connection; the machine adds no close
or keep-alive field for a switch. After `sent` returns `switched`, the machine
stops parsing HTTP and disables its deadlines.
`remainingInput` returns bytes read past the request. They remain the next
protocol's bytes; they are never sent through the HTTP parser. The engine
currently closes such a connection after the 101 because fd handoff is not an
engine hook yet; a direct driver can keep it.

A normal `Request.head` and its field slices live until the response completes.
A handler can review a rejection through `policy_response`, using the request
arena for its body. `PolicyContext.reason` has the parser or framing category,
not just the status. `.reject` carries both. Conflicting lengths, invalid
lengths, framing conflicts, unsupported chunking, Host failures, malformed
heads, field limits, head/body limits, and timeouts are distinct.
 This includes framing rejections before a head event. The
head may be absent; `PolicyContext` exposes the slot, status, and arena only.
The default response keeps the chosen status with an empty body. For a normal
response, set `ResponseOptions.close` to close the connection without supplying
a `Connection` field manually.
A `request_head` head must remain valid through a call to `acceptBody` or
`bufferBody`, and its storage must then survive the following `request` event.
When the caller responds from `request_head` without accepting a body, it may
copy the fields it needs immediately and reuse the header storage after the
response completes. No field slice survives that reuse. The `ServerConn` test
with shared storage covers this short-lived refusal path.

The machine writes Content-Length, then Connection when the version needs it,
then the caller's fields.

Leading LF or CRLF bytes remain empty-line syntax (RFC 9112 §2.2). They do not
start the head or total deadline and do not end idle. A close after only those
bytes is a clean `.closed`. Once the first request-line byte arrives, the normal
head and total deadlines apply.

Keep-alive follows RFC 9112 §9.3. HTTP/1.1 persists by default. HTTP/1.0
persists only with `Connection: keep-alive`. A close request or a policy
response closes after the response. Bytes after the request stay in the
request buffer, so a pipelined request needs no extra read.

A HEAD request receives the representation's Content-Length but no body. The
caller passes the representation to `respond`; the machine sends the head
only. A 204 or 304 response ignores the body and omits Content-Length. A final
1xx status is `error.InvalidStatus`; the machine owns the 100 Continue.
An HTTP/1.0 request never receives 100 Continue; the machine reads its body
directly.

`Limits` holds the body limit and six timeouts: idle, head, body, write
progress, total, and drain. A zero duration disables that timeout, except
`drain_timeout`, where zero skips the drain and closes. `deadline`
returns the earliest active deadline. The idle timeout starts at accept and
after a keep-alive response. The first request byte replaces it with the head
timeout and starts the total timeout. The total timeout restarts for each
request. The write timeout restarts on every `sent` call. The drain timeout
starts when `close_after_drain` is returned.

## Client connection

`h1.ClientConn` is the response-side state machine for one request at a time.
It is sans-I/O and allocates nothing. The caller supplies the receive buffer,
the response field storage, and optional trailer storage, writes the request
with `h1.Writer`, then drives the response.

Call `start(method)` before writing a request. The method is needed for the
HEAD and CONNECT framing rules. The loop:

1. Call `recvBuffer`. Read into the returned slice.
2. Call `received`. `need_more` repeats step 1. `response` carries the head and
   the chosen `h1.framing.ResponseBody`; call `next` for its body.
3. `next` returns a borrowed `body` slice, `done`, or `need_more`. A body slice
   is valid until the next call. After `done`, call `start` for the next
   request; bytes left in the receive buffer are preserved.
4. Call `eof` when the peer closes. A zero-byte read is not passed to
`received`; `received` asserts `n > 0`, so an empty transport completion cannot
turn into a policy 400 by accident. A close before any bytes is `closed`; a
   close in a head or a length/chunked body is `error.Incomplete`. A
   close-delimited body ends with `done`.

An interim 1xx head is a `response` like any other. It has no body; call
`start` again to parse the final response from the remaining bytes. Body bytes
are never buffered by the machine: the caller consumes the slice before the
next read.

`Config.body_bytes` limits the bytes delivered to the caller. `BodyTooLarge`
is returned before the limit is exceeded. Chunked trailers are parsed into
`Config.trailers`; an empty slice rejects a trailer section. A 101 or CONNECT
tunnel is reported in `framing` and ends the HTTP response; the connection
handoff belongs to the caller.

### Blocking adapter

`h1.client.blocking.fetch` is the convenience layer over `ClientConn`. It takes
a `Request` (method, target, fields, optional body) and a `Config` holding the
receive buffer, response field storage, trailer storage, body destination, and
request write buffer. It writes HTTP/1.1, adds Content-Length when the caller
did not frame the body, reads one response, and returns the head, framing, and
a body slice borrowed from `Config.body_buffer`.

It does not allocate, does not own the stream, and does not reuse the
connection. `fetchIo` is the same operation over caller-owned plaintext
`Io.Reader` and `Io.Writer` interfaces; the TLS example calls it after the
handshake. The caller must close the stream and keep `Config` alive while the
returned head is in use. If the response body exceeds `body_buffer`, `fetch`
returns `error.BodyTooLarge`. A response with no `Content-Length` and no chunked
coding is read until EOF.

`just interop` builds `tools/http1-interop`, a Go `net/http` server, and runs
`examples/http1_client.zig` against its Content-Length, chunked, and echo
routes.
