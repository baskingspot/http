# HTTP/1.1 head parsing: references and choices

The parser in `src/h1/root.zig` is written from the RFCs, not ported from C.
`picohttpparser` supplied the incremental-read contract (`last_len`) and its
test corpus informed the table below; `hparse` 0.2.0 is kept as a benchmark
reference, not as a base.

## Normative references

- [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112): HTTP/1.1 message syntax
  and routing. §2.1 message format, §2.2 parsing and line terminators, §2.3
  HTTP-version, §3 request line, §3.1 method, §3.2 request-target, §4 status
  line, §5 field syntax, §5.1 field line parsing, §5.2 obs-fold.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110): HTTP semantics. §2.5
  protocol version semantics, §6.2 control data and the higher-minor rule,
  §5.1 fields, §5.5 field values, §5.6.2 token and
  tchar, §5.6.3 OWS, §15 status codes.
- [RFC 5234](https://www.rfc-editor.org/rfc/rfc5234): ABNF core rules.
- [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986): URI syntax, referenced by
  the request-target forms.

## Choices where the RFC permits more than one behavior

| Subject | RFC | Choice |
| --- | --- | --- |
| Bare LF as a line terminator | 9112 §2.2 (MAY recognize) | Reject. |
| Lenient start-line whitespace | 9112 §3, §4 (MAY parse on whitespace) | Reject; exactly one SP. |
| obs-fold | 9112 §5.2 (reject or unfold) | Reject. |
| Whitespace before the first field | 9112 §2.2 (reject or consume) | Reject. |
| Leading empty lines before a request-line | 9112 §2.2 (SHOULD ignore) | Skip any number. |
| Minor version above 1 | 9110 §6.2 (process as highest supported) | Map to 1.1; keep the wire pair in `wire_version`. |
| Status codes outside 100..599 | 9110 §15 (invalid) | Return the three digits as an open `Status`; the caller applies the class rule. |
| Request-target form | 9112 §3.2 | No whitespace and printable ASCII; the origin/absolute/authority/asterisk choice is routing policy. |
| Missing or duplicate Host | 9112 §3.2 (server MUST 400) | Parse the fields; the server layer enforces it. |
| Header storage exhaustion | — | `error.TooManyHeaders`, distinct from invalid syntax. |

## Lifetimes

`parseRequest` and `parseResponse` return a head that borrows the input buffer
and the caller's `Header` storage. The head is valid only while both are
unchanged. A buffered reader may move its bytes when it refills or rebases;
copy the target, reason, and any field values needed later before the next read
or rebase. The parsed `method`, `version`, and `wire_version` are plain values.

## Incremental reads

`last_len` is the number of bytes already searched for `CRLF CRLF`. On a later
call the completeness check starts at `last_len - 4`, so only new bytes are
scanned; parsing still starts at byte 0. A client trickling one octet at a time
therefore cannot force a full rescan on every read.

## Message body framing

`h1.framing` applies RFC 9112 §6.3 in order. `request` returns a
`RequestBody`: `none`, `length`, or `chunked`. `response` returns a
`ResponseBody`, which adds `close` and `tunnel`. It reads the head only; it
does not read the body.

| Subject | RFC | Choice |
| --- | --- | --- |
| HEAD, 1xx, 204, 304 | 9112 §6.3 rule 1 | `none`, whatever the fields say. |
| 2xx response to CONNECT | 9112 §6.3 rule 2 | `tunnel`; ignore Content-Length and Transfer-Encoding. |
| Transfer-Encoding and Content-Length together | 9112 §6.3 rule 3 (TE overrides, ought to be an error) | Reject as `error.ConflictingFraming`. |
| Transfer-Encoding on HTTP/1.0 | 9112 §6.1 (faulty framing) | Reject as `error.FaultyFraming`. |
| Transfer-Encoding on a request, final coding not chunked | 9112 §6.3 rule 4 (server MUST 400) | Reject as `error.InvalidTransferEncoding`. |
| Transfer-Encoding on a response, final coding not chunked | 9112 §6.3 rule 4 | `close`. |
| Content-Length, no Transfer-Encoding | 9112 §6.3 rule 6 | `length`; malformed, conflicting, or overflowing values are `error.InvalidContentLength`. |
| Request with no framing fields | 9112 §6.3 rule 7 | `none`. |
| Response with no framing fields | 9112 §6.3 rule 8 | `close`. |

`chunked` takes no parameters and must appear at most once. The framing result
is the input to the chunked decoder.

## Chunked bodies

`h1.chunked.Decoder` decodes RFC 9112 §7.1. `next` returns a `Step`: a borrowed
data slice, the trailer `Headers`, or `need_more`. `consumed` is the prefix to
drop on every step, including `need_more`, so the caller can append bytes and
retry without copying the whole body. A chunk data slice may end before the
chunk does; the decoder remembers the remaining count.

Chunk extensions are parsed and ignored. A chunk size that does not fit `u64`
is `error.Overflow`; a malformed size, CRLF, extension, or trailer is
`error.Invalid`. Trailers are returned separately; the caller decides which
fields can be merged (RFC 9110 §6.5.1).

## Connection persistence

`h1.persistent(version, headers)` applies RFC 9112 §9.3. HTTP/1.1 persists by
default; HTTP/1.0 persists only with the `keep-alive` connection option; a
`close` option wins on either version.
