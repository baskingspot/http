# HTTP/2 framing: references and choices

The frame codec in `src/h2/frame.zig` is written from RFC 9113, not ported from
an implementation. h2c and h2 over TLS use the same frames; nothing in this
module touches TLS or reads the connection preface.

## Normative references

- [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113): HTTP/2. §3.4 connection
  preface, §4.1 frame format, §4.2 frame size, §5.1 stream identifiers, §6.1
  DATA, §6.2 HEADERS, §6.3 PRIORITY, §6.4 RST_STREAM, §6.5 SETTINGS, §6.6
  PUSH_PROMISE, §6.7 PING, §6.8 GOAWAY, §6.9 WINDOW_UPDATE, §6.10
  CONTINUATION, §7 error codes.
- [RFC 7541](https://www.rfc-editor.org/rfc/rfc7541): the field block carried
  by HEADERS and CONTINUATION.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110): field names, values, and
  status codes, referenced by §8.2.1 of HTTP/2.
- [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441): extended CONNECT and the
  `:protocol` pseudo-header.
- [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986): scheme and authority
  syntax.

## Choices

| Subject | RFC | Choice |
| --- | --- | --- |
| Unknown frame types | 9113 §4.1 (MUST ignore) | `body` returns `Body.unknown` with the raw payload; the caller discards it. |
| Unused flags | 9113 §4.1 (MUST ignore on receipt) | Left in `Header.flags`; the payload parser checks only the flags it defines. |
| Reserved stream bit | 9113 §4.1 (MUST ignore on receipt, zero on send) | Masked off on parse; zero on encode. |
| Payload above SETTINGS_MAX_FRAME_SIZE | 9113 §4.2 | `parse` takes the current maximum and returns `error.FrameTooLarge` before waiting for the payload. The caller maps it to FRAME_SIZE_ERROR. |
| Fixed payload lengths | 9113 §6.3–6.10 | PRIORITY 5, RST_STREAM 4, PING 8, GOAWAY at least 8, WINDOW_UPDATE 4, SETTINGS a multiple of 6, ACK SETTINGS empty. Anything else is `error.InvalidLength`, which maps to FRAME_SIZE_ERROR. |
| Padding | 9113 §6.1, §6.2, §6.6 | Stripped from DATA and the block fragments. A pad length that covers the whole payload is `error.InvalidPadding`, which maps to PROTOCOL_ERROR. Padding bytes are not checked for zero. |
| PRIORITY in HEADERS | 9113 §6.2 | Parsed when the flag is set; priority signaling is deprecated but the fields are still on the wire. |
| WINDOW_UPDATE of zero | 9113 §6.9 | Kept as the wire value; the flow-control layer rejects it. |
| Stream 0, frame ordering, SETTINGS values | 9113 §5.1, §6.5, §4.3 | Not checked here. The frame codec is syntax only; the stream and connection layers own those rules. |
| CONTINUATION | 9113 §4.3, §6.10 | Parsed as a fragment. Assembly across frames belongs to the layer above. |
| Partial reads | — | `parse` returns `error.Incomplete` until the 9-byte header and all `Length` payload bytes are present. The header carries the length, so there is no rescan cursor like HTTP/1. |
| Writing | — | `Writer` fills a caller buffer: `begin` reserves the 9-byte header, `bytes`/`int` append the payload, `end` patches the 24-bit length. A short buffer is `error.NoSpace` and leaves the partial frame at `pos`. |

## Field sections

`h2.head.request` and `h2.head.response` take the field list the HPACK decoder
produced, pseudo-headers included, and return a typed head plus a `Headers`
view of the regular fields. Every slice is borrowed; the head owns nothing.

| Subject | RFC | Choice |
| --- | --- | --- |
| Field names | 9113 §8.2.1 | Lowercase `tchar` only. Stricter than the RFC's minimal list of forbidden bytes, and the same rule HTTP/1.1's parser applies. |
| Field values | 9113 §8.2.1, 9110 §5.5 | NUL, CR, LF, other controls, DEL, and edge SP/HTAB are rejected. HTAB inside a value and obs-text are allowed. |
| Pseudo-header order | 9113 §8.3 | Pseudo-headers must precede regular fields. A pseudo after a regular field is `PseudoAfterField`. |
| Pseudo-header duplication | 9113 §8.3 | One of each; a repeat is `DuplicatePseudo`. |
| Pseudo-header names | 9113 §8.3.1, §8.3.2, RFC 8441 | Requests: `:method`, `:scheme`, `:authority`, `:path`, `:protocol`. Responses: `:status`. Anything else is `UnknownPseudo`. |
| Required request fields | 9113 §8.3.1 | `:method`, `:scheme`, and `:path`, unless CONNECT. |
| CONNECT | 9113 §8.5 | `:scheme` and `:path` omitted; `:authority` required. |
| Extended CONNECT | RFC 8441 | `:protocol` present with CONNECT, and `:scheme`, `:path`, `:authority` required. `:protocol` without CONNECT is `InvalidProtocol`. |
| `:path` | 9113 §8.3.1 | Non-empty and absolute. `*` is accepted only for OPTIONS. |
| `:scheme` | RFC 3986 §3.1 | ALPHA, then ALPHA / DIGIT / `+` / `-` / `.`. Not limited to http and https. |
| `:authority` | 9113 §8.3.1 | Non-empty. Userinfo (`@`) is rejected for http and https. Host and port syntax is left to the URI layer. |
| `:status` | 9113 §8.3.2, 9110 §15 | Exactly three digits. The value is an open `Status`; the caller applies the 100..599 class rule. |
| `:method` | 9113 §8.3.1, 9110 §9.1 | A non-empty token. `Method.parse` fills the common enum, and `method_token` keeps the exact bytes. |
| Connection-specific fields | 9113 §8.2.2 | `connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, and `upgrade` are rejected. `te` must be exactly `trailers`, case-insensitively. |
| Cookies | 9113 §8.2.3 | Not combined. The caller combines `cookie` lines with `"; "` where it wants the joined value. |
| `host` and `:authority` mismatch | 9113 §8.3.1 (SHOULD malformed) | Not checked; normalization is the caller's policy. |
| Malformed section | 9113 §8.1.1 | A stream error of type PROTOCOL_ERROR. `h2.head.Error` carries the reason. |

## Settings

`h2.settings.Values` is one direction's SETTINGS: the local values this
endpoint advertises, or the remote values the peer sent. The defaults are RFC
9113 §6.5.2's: 4,096-byte header table, push enabled, no concurrent-stream or
header-list limit, 65,535-byte initial window, 16,384-byte maximum frame.

`apply` validates `ENABLE_PUSH` (0 or 1, and a client rejects a server sending
1), `INITIAL_WINDOW_SIZE` (≤ 2^31−1), and `MAX_FRAME_SIZE`
(16,384..16,777,215). The last value wins and unknown identifiers are ignored.
A change to the initial window is not applied to stream windows here; the flow
layer applies the delta.

## Flow control

`h2.flow.Window` is signed. A send window can go negative when the peer lowers
`SETTINGS_INITIAL_WINDOW_SIZE` below the bytes already sent, and the sender
waits for WINDOW_UPDATE. `consume` accounts DATA, `increase` applies a
WINDOW_UPDATE (zero is `ZeroIncrement`, an increase above 2^31−1 is
`FlowControlError`), and `applyInitialChange` applies the setting delta to one
stream window.

The module does not decide connection versus stream errors. The session maps
`FlowControlError` and `ZeroIncrement` per RFC 9113 §5.2 and §6.9.

## Stream states

`h2.stream.transition` applies one frame event from one side to a state. A
HEADERS frame with END_STREAM is `headers` then `end_stream`, so the state
matches the frame. Trailers are legal only on the side that is still open.
`reset` closes an active stream and is `IdleStream` on an idle one, which is a
connection error. `push_promise` reserves the promised stream.

`h2.stream.Ids` allocates local identifiers with the role's parity and accepts
remote ones only when the parity matches the peer and the identifier is
greater than the last seen.

## Header block assembly

`h2.header_block.Assembler` takes the HEADERS or PUSH_PROMISE fragment and the
CONTINUATION fragments that follow. A single-frame block is returned borrowed
from the input; a split block is copied into the caller's buffer. A new start
while a block is open is `Interleaved`, a stray or wrong-stream CONTINUATION is
`UnexpectedContinuation`, and a block that outgrows the buffer is `TooLarge`.
While a block is open, RFC 9113 §4.3 allows no other frame on the connection;
the caller checks `isAssembling`.

## Session

`h2.Session` is the sans-I/O connection machine. It owns the preface,
SETTINGS, the stream table, HPACK, flow control, CONTINUATION assembly, and the
outbound queue. It has no socket, TLS type, event loop, or stored allocator.

| Call | Purpose |
| --- | --- |
| `init(allocator, .{ .role = ... })` | Build the session and queue the preface (client) and initial SETTINGS. |
| `receive(bytes) usize` | Append transport bytes; returns how many fit. |
| `nextEvent(allocator) !?Event` | Parse until one event is ready; null means more bytes. |
| `submitRequest/Response/Trailers/Data/Reset/Goaway/Ping` | Queue frames. |
| `submitSettings` | Queue a local SETTINGS change and apply its receive-side effects. |
| `release(allocator, id, count)` | Return consumed DATA bytes to both windows. |
| `send(out) usize` | Copy queued bytes into the transport buffer. |
| `deinit(allocator)` | Free the stream map, pools, tables, and buffers. |

Events are `request`, `response`, `data`, `trailers`, `reset`, `window_update`,
`goaway`, and `connection_error`. A `reset` carries `origin` so the caller can
tell a local stream error from a peer reset. `data` carries the payload with
padding removed and `flow_len` for the whole padded payload. Event slices are
borrowed from the input buffer or the decoded-field buffer and stay valid until
the next `nextEvent`.

Connection errors are events: the session queues `GOAWAY` and sets `isClosed`;
the caller drains `send` and closes. Stream errors queue `RST_STREAM` and arrive
as a local `reset`. A malformed HPACK block is a connection error
`COMPRESSION_ERROR`; a bad field section is a stream error `PROTOCOL_ERROR`; a
frame larger than our `MAX_FRAME_SIZE` is `FRAME_SIZE_ERROR`.

A closed stream keeps a small tombstone ring, so a late frame gets the right
answer. DATA on a closed stream is a stream error `STREAM_CLOSED`; a HEADERS
after a reset is also `STREAM_CLOSED`; a HEADERS after both sides ended is a
connection error `STREAM_CLOSED`, because the stream was closed without a
reset. A remote identifier below the last one that was never opened is a
connection error `PROTOCOL_ERROR`. A HEADERS or PRIORITY frame whose dependency
is the stream itself is a stream error `PROTOCOL_ERROR`; a second HEADERS
(trailers) must carry END_STREAM.

A non-ACK SETTINGS frame produces a `settings` event with the values the peer
just set. The application uses it to resume work after a window change, such as
pending DATA that was waiting on `INITIAL_WINDOW_SIZE`.

`submitSettings` sends a local change. It applies the receive side immediately:
`INITIAL_WINDOW_SIZE` adjusts every open stream's receive window, and a value
that would overflow a window is rejected. `MAX_FRAME_SIZE`, `HEADER_TABLE_SIZE`,
`MAX_HEADER_LIST_SIZE`, and `MAX_CONCURRENT_STREAMS` are capped by what `init`
allocated, so a fixed-storage session cannot advertise more than it can hold. A
server cannot send `ENABLE_PUSH`, and this session never advertises push.

The memory model is the one from the state layer: no allocator is stored. The
stream map is reserved to `max_streams` at init, stream records and output
chunks come from `std.heap.MemoryPool`, and the HPACK tables and header/field
buffers are allocated once. A `std.heap.FixedBufferAllocator` is a valid
fixed-ceiling allocator because the pools reuse records and chunks; an
allocation failure is `error.OutOfMemory`.

`submitData` accepts a prefix of the input, bounded by the stream and
connection send windows, `MAX_FRAME_SIZE`, and `max_out_bytes`. It returns the
accepted count; the caller keeps the rest. `release` sends the two
WINDOW_UPDATE frames and increments both receive windows. Padding is returned
automatically; the caller releases the data bytes it consumed.

`max_out_bytes` caps queued output. A header submission returns
`error.WouldBlock` when the cap is reached; `submitData` returns a smaller
prefix. Control frames (ACK, RST_STREAM, GOAWAY) are not blocked by the cap.

Push is not implemented: a received `PUSH_PROMISE` is a connection error
`PROTOCOL_ERROR`. PRIORITY is parsed enough to reject a self-dependency, then
ignored. TLS enters only at the I/O layer through ALPN; the session is h2c and
h2 alike.

The h2c example is the conformance target: it serves connections on threads,
waits for the request to end before it answers, and resumes partial DATA when
flow control opens. `just conformance` runs h2spec against it; the full suite
passes, strict included. `just load` runs h2load.

## Engine

`h2.engine.blocking` is the transport layer over the session, the h2
counterpart to `h1.engine.blocking`. The engine buffers one complete request per
stream, hands it to the application as an `Exchange`, and pumps the response
under flow control. It matches h1's trade: convenient request/response
handling, not a streaming API. Use `h2.Session` directly when the application
needs to stream bodies or drive the protocol itself.

`serve` takes one `Io.net.Stream` and runs the read/event/write loop; `run` is
the accept loop, one connection at a time. The engine owns the session, the
socket, the transport buffers, and a fixed slot table of `max_streams` entries.
Each slot owns an `ArenaAllocator`; the copied request head, trailers, and body
live there until `complete`. The response fields do not: the status text,
content-length text, and up to `max_response_headers` field records live in the
`Exchange`, so `respond` allocates nothing.

An `Exchange` is one request. Its `request` has the typed head, the whole body
up to `Config.body_bytes`, and the trailers. `respond(options, body)` records
the response; the engine adds `:status` and `content-length`, validates the
field section through `h2.head.response`, sends the HEADERS, and pumps the body
under flow control. The body and any extra header slices are borrowed; they
must stay valid until `complete`.

The handler is a type-erased vtable:

| Entry | Meaning |
| --- | --- |
| `handle(ptr, exchange)` | Build the response. The engine supplies a 500 if the handler returns without one. |
| `complete(ptr, exchange)` | The response is queued, the stream was reset, or the connection ended. The arena is still readable; the engine resets it afterward. |
| `report_error(ptr, err)` | `handle` failed, or the engine could not serve the connection. |

The engine enforces `content-length` against the received DATA, caps request
bodies, refuses streams when the slot table is full, and resumes a response
when flow control or the output budget opens. `max_streams` is both the slot
count and the session's advertised `MAX_CONCURRENT_STREAMS`; `body_bytes` is per
request, so the worst-case live body memory is roughly `max_streams ×
body_bytes`. `Config.allocator` backs the session, the slots, and the
per-stream arenas.

The h2c example is this engine with a thread per accepted connection. `just
conformance-run` runs h2spec against it; the full suite passes, strict
included.

## h2c and TLS

h2c and h2 share every frame. The only differences sit below this module: the
client preface (`frame.preface`) and, for h2, ALPN during the TLS handshake.
The server's first frame after the preface is SETTINGS in both cases. Nothing
in the codec needs a TLS type.
